# prober

Synthetic warm-path latency prober for PowerBlockade. Continuously walks a
frozen control corpus through the dnsdist edge and reports client-observed
latency. This is the ground-truth latency signal, kept deliberately separate
from production traffic metrics: no retries, no persistence, no admin-ui
integration.

## Identity contract

The prober's dnstap source IP **is** its identity. The compose service pins
`ipv4_address: 172.30.0.30` on the `powerblockade` network; the dnstap
processor classifies that IP before observing metrics. Do not run the prober
from any other address, or its traffic will be mixed into user analytics.

## Metrics

Served on `:9533` (`/metrics`, plus `/healthz`), scraped over the compose
network only (no host publication). Uses the standard Prometheus Go client
registry, exposed through a dedicated registry containing only:

| Metric | Type | Meaning |
|--------|------|---------|
| `powerblockade_prober_queries_sent_total` | counter | queries sent to the edge |
| `powerblockade_prober_queries_answered_total` | counter | queries that got any DNS response |
| `powerblockade_prober_queries_refused_total` | counter | answers with rcode REFUSED |
| `powerblockade_prober_queries_timed_out_total` | counter | queries exceeding the timeout (never retried) |
| `powerblockade_prober_queries_errored_total` | counter | transport errors other than timeout |
| `powerblockade_prober_query_latency_seconds` | histogram | client-observed send→response latency |
| `powerblockade_prober_pass_duration_seconds` | gauge | duration of the last full corpus pass |
| `powerblockade_prober_pass_queries` | gauge | query count of the last pass |

Histogram buckets (seconds): `0.0001, 0.00025, 0.0005, 0.001, 0.0025, 0.005,
0.01` — the same boundaries as the dnstap-processor latency histograms, so
dashboards can overlay client-observed and server-observed latency.

## Configuration (environment)

| Variable | Default | Meaning |
|----------|---------|---------|
| `PROBE_TARGET` | `dnsdist:53` | DNS edge to probe |
| `PROBE_CORPUS` | `/usr/local/share/powerblockade/corpus/control-domains.txt` | frozen corpus path (mounted read-only by compose) |
| `PROBE_INTERVAL` | `60s` | pass cadence (start-to-start) |
| `PROBE_JITTER_PCT` | `10` | ±jitter on the interval, percent (0 disables) |
| `PROBE_TIMEOUT` | `2s` | per-query timeout; a timeout is final |
| `PROBE_QTYPES` | `A` | comma-separated query types (e.g. `A,HTTPS`) |
| `PROBE_METRICS_ADDR` | `:9533` | metrics listen address |

## Control corpus

The compose stanza mounts `scripts/benchmarks/corpus` (read-only) at
`/usr/local/share/powerblockade/corpus`. The checked-in corpus is FROZEN:
10,000 domains taken in rank order from the Cisco Umbrella top-1M ranking
(DNS-resolution volume), generated by
`scripts/benchmarks/corpus/fetch-top-domains.sh`. Never edit it in place —
regenerate deliberately (the script takes a count argument) and treat the
change as a new corpus version, because every latency comparison before and
after it is no longer apples-to-apples. The separate hand-curated set under
`docs/performance/corpus/` belongs to `dns53-benchmark.sh`; the prober does
not use it.

## Behavior notes

- One send per query. A timeout counts as a timeout; there are no retries.
- The UDP socket is connected once and reused across queries so the
  client-side path stays warm. A failed socket is dropped and redialed on the
  next query — the failed query itself is never resent.
- Pass cadence: each pass starts `PROBE_INTERVAL ± PROBE_JITTER_PCT%` after
  the previous pass started. A pass that overruns its interval shortens the
  sleep (never below zero).
